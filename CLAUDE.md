# Is My Train Screwed? — Project Context

Full spec: `is-my-train-screwed-spec.md` (read it for anything not covered below — this file is orientation, not a substitute).

## What this is

Conversational NYC transit trip advisor (PWA). Differentiates on judgment, not routing: empirical (never LLM-guessed) transfer-miss probabilities, proactive monitored-trip re-planning, accessibility/luggage-aware routing, and a data-gated airport mode (LGA first). Beachhead users: Cornell Tech / Roosevelt Island subway commuters.

## Hard rules (violating these is a spec bug, not a style nit)

- **LLM agents never compute numbers, routes, or probabilities.** They call tools and narrate tool output only. If you catch yourself writing a prompt that asks a model to produce a number, stop — the fix is always better data or an honest "insufficient data (n<200)" response.
- **Model choice is a config/env parameter per agent, never hardcoded.** Default Haiku 4.5 everywhere; never Opus/flagship tier for anything in this product.
- Bus corridor probabilities/airport mode only surface once that corridor's data crosses `n≥200` observations — data-gated, not date-gated.
- The only autonomous write path any agent has is appending a validated entry to bus-corridor collector config (Coverage-Expansion Agent). Everything else escalates to Frank.
- Never mock/stub/hardcode fake credentials "to keep moving." If something's missing, build what doesn't depend on it and flag what's blocked — don't fake it.

**Deployment gotchas that only surfaced live (none caught by local tests — all required real `railway ssh`/log inspection to find):**
- **A service created with `branch: "X"` before `X` exists on GitHub silently falls back to the repo's default branch (`main`)** — no error, no warning. Hit this for *both* `otp` and `backend` (the `phase2-risk-engine` branch was only pushed partway through this deploy). Symptom for `otp`: Dockerfile not found at the expected path. Symptom for `backend`: deployed fine and reported `SUCCESS`, but was silently running pre-Phase-2 `main` code (had `/health` but no `/chat`, no `/proxy` mount) — this one is *much* more dangerous than an outright failure, since it looks successful. **Always verify a deployment's actual `meta.commitHash` matches what you expect**, don't trust `status: SUCCESS` alone. Fix: `serviceConnect(id, {repo, branch})` then `serviceInstanceDeploy(..., latestCommit: true)`.
- **A Docker volume mounted at the same path a `Dockerfile`'s `COPY` writes to silently shadows the image's files.** `otp_config/Dockerfile` copies `router-config.json` into `/var/opentripplanner/`, but the `otp-volume` is *also* mounted there (needed for `graph.obj`) — so the image's copy never actually appears in the running container; only `graph.obj` (manually uploaded to the volume) is visible. OTP doesn't error on a missing `router-config.json` — it silently falls back to whatever router config was **embedded in `graph.obj` at build time** (a real, documented OTP behavior: "OTP uses the config embedded in the loaded graph if no new [external] config is provided"). Since `graph.obj` was built locally with `docker-compose.yml`'s local dev value (`REALTIME_PROXY_BASE_URL=http://host.docker.internal:8090`), that literal URL got baked into the graph and silently overrode the intended `${REALTIME_PROXY_BASE_URL}`-parameterized production value. **Fix applied (works, but operationally fragile — not yet fixed at the architecture level): manually `railway ssh`-upload the real (still-`${VAR}`-templated) `backend/otp_config/router-config.json` directly onto the `otp-volume` alongside `graph.obj`, then redeploy.** OTP's own native env-var substitution then correctly resolves `${REALTIME_PROXY_BASE_URL}` against the `otp` service's real env var at load time. **Caveat for future sessions: if `graph.obj` is ever re-uploaded (e.g., after a future local rebuild), `router-config.json` must be re-uploaded too**, or the newly-uploaded graph's embedded (local-dev) config will silently take over again. A cleaner permanent fix would mount the volume at a different path (e.g. `/data/graph`) and have the startCommand `cp` `graph.obj` into `/var/opentripplanner/` before `--load`, letting `router-config.json` stay a normal git-tracked, auto-deployed file — not implemented yet, flagged here as a known follow-up.
- **`backend`'s realtime-proxy mount (`/proxy`) and the `find_stop`/`get_risk` tools all need real GTFS zip files that are gitignored** (`backend/data/gtfs/*.zip` — `subway.zip` for `TripIndex`, plus all 7 files for `StopIndex`/`RouteIndex`, per Tasks 6 and 9). These were never part of any git-based deploy and had to be `railway ssh`-uploaded manually to `/app/data/gtfs/` on `backend-volume`. `subway.zip`'s absence crashed the whole app at startup (the realtime-proxy's `lifespan` needs it immediately); the other 6 would have crashed a *later*, harder-to-diagnose way — the first time a real user query happened to trigger `find_stop` or a multi-leg `get_risk` call. Uploaded all 7 proactively rather than waiting to hit that.
- **A container that's crash-looping (missing data, OOM, etc.) refuses `railway ssh`** (`"container is not running (status: exited)"`) — needed to temporarily override `startCommand` to `sleep infinity`, redeploy, do the SSH upload, then restore the real `startCommand` and redeploy again. Used this pattern 3 times across the two services during this deploy.
- **Railway's public-domain routing can get stuck returning its own edge-level `{"code":404,"message":"Application not found"}`** (distinct from the app's own 404 — check the response body, not just the status code, to tell them apart) even when the app itself is confirmed reachable via private networking and correctly configured (`targetPort` matched the app's real listening port). Fix: delete and recreate the `serviceDomain` — resolved it immediately both times it happened. Root cause not fully understood; if it recurs, this is the fix, not a deeper investigation.
- **Docker is not accessible from this Claude Code session's sandbox** (confirmed via both Bash and PowerShell — the binary isn't present, not just missing from PATH; the `!` prefix doesn't help either, since it still runs inside the same sandbox, not a separate host shell). Every local OTP graph build in this deploy had to be run by the user directly, in their own terminal — this will be true for any future local graph rebuild too.
- **pyosmium has no built-in bounding-box extraction** — its own maintainers direct users to the separate `osmium-tool` C++ binary (not pip-installable, wasn't available here). A manual two-pass Python implementation (see `trim_osm_extract.py`) is fine for a one-off admin operation despite being slower than the native tool.

**End-to-end verification performed (all real, live calls — not mocked):** `POST /chat` with a real message returns a real, non-canned Anthropic response; a real routing question ("Roosevelt Island to Lex/63") correctly invokes `plan_route` (reaching `otp` via `http://otp.railway.internal:8080` private networking), returns the real F-train itinerary, and correctly narrates "no transfers needed" (i.e. `get_risk` correctly returned `[]`, not a fabricated number) since it's a single-leg trip; `/proxy/rt/g` returns 200 through the mounted sub-app; OTP's subway real-time updaters show real, working (not erroring) partial match rates consistent with Phase 1's documented per-feed numbers (33-45% on the numbered/lettered feeds sampled); the low bus real-time match rate (0.4-0.65%) is expected and correct, not a bug — it's the direct, intentional consequence of trimming the static bus GTFS to 3 routes while the live feed itself still carries all ~300+ MTA bus routes' trips.
