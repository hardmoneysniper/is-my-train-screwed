# Is My Train Screwed? — Project Context

Full spec: `is-my-train-screwed-spec.md` (read it for anything not covered below — this file is orientation, not a substitute).

## What this is

Conversational NYC transit trip advisor (PWA). Differentiates on judgment, not routing: empirical (never LLM-guessed) transfer-miss probabilities, proactive monitored-trip re-planning, accessibility/luggage-aware routing, and a data-gated airport mode (LGA first). Beachhead users: Cornell Tech / Roosevelt Island subway commuters.

## Hard rules (violating these is a spec bug, not a style nit)

- **LLM agents never compute numbers, routes, or probabilities.** They call tools and narrate tool output only. If you catch yourself writing a prompt that asks a model to produce a number, stop — the fix is always better data or an honest "insufficient data (n<200)" response.
- **Model choice is a config/env parameter per agent, never hardcoded.** Default Haiku 4.5 everywhere; never Opus/flagship tier for anything in this product.
- Bus corridor probabilities/airport mode only surface once that corridor's data crosses `n≥200` observations — data-gated, not date-gated.
- The only autonomous write path any agent has is appending a validated entry to bus-corridor collector config (Coverage-Expansion Agent). Everything else escalates to Frank.
- Never mock/stub/hardcode fake credentials "to keep moving." If something's missing, build what doesn't depend on it and flag what's blocked — don't fake it.
- **Do everything the minimal way. Don't add structure (new services, new UI surfaces, new dependencies, new abstractions) that isn't absolutely needed.** When a smaller change solves the real problem, use it — e.g. Task 11 became a system-prompt format change + one small rendering tweak instead of a new provenance UI; the subway trip-id fix became a ~90-line proxy instead of a Phase 2 rebuild. **Exception:** building a spec-mandated piece ahead of its first caller is fine when a later, already-planned phase is the known consumer (e.g. `StopIndex` built in Phase 1 for Phase 2's free-text location lookup) — the rule targets speculative or unnecessary structure, not sequencing infrastructure before the phase that uses it. It does NOT excuse skipping a check for whether a platform/library already solves the problem before building custom tooling (see the OTP-native `${VAR_NAME}` config-substitution fix — that was avoidable custom structure, not planned-ahead infrastructure).

A cleaner permanent fix would mount the volume at a different path (e.g. `/data/graph`) and have the startCommand `cp` `graph.obj` into `/var/opentripplanner/` before `--load`, letting `router-config.json` stay a normal git-tracked, auto-deployed file — not implemented yet, flagged here as a known follow-up.

- **Railway's public-domain routing can get stuck returning its own edge-level `{"code":404,"message":"Application not found"}`** (distinct from the app's own 404 — check the response body, not just the status code, to tell them apart) even when the app itself is confirmed reachable via private networking and correctly configured (`targetPort` matched the app's real listening port). **The `reliability_buckets` EWMA bug — the most consequential finding of this push.** Checking whether empirical risk citations actually fire in production (they didn't — every test query returned `quality="insufficient"`) led to discovering `n_observations` was capped in the single digits to ~19 even after a full 90-day subway backfill (16.4M real events) and continuous bus collection, nowhere near `risk_engine.py`'s `MIN_N_OBSERVATIONS = 200` gate. Root cause, traced to `scripts/aggregate_reliability_buckets.py`'s nightly fold: `n_observations = 0.95*old + 0.05*today` is an exponentially weighted moving average whose **steady-state magnitude converges to roughly one day's raw count** (`0.05 / (1 - 0.95) = 1`) — a mathematical ceiling completely independent of how many days of real history get folded in. This is a genuine cross-task integration gap: `task-6-brief.md` correctly derived `MAX_WINDOW_DAYS = 20` from this same formula's *memory horizon* (how many days it still "remembers"), but nobody separately checked whether a realistic bucket's *magnitude* could ever cross the unrelated `MIN_N_OBSERVATIONS = 200` threshold — it structurally couldn't, for subway or bus, ever, regardless of collection time. Not a missing-data problem; syncing more data into the same broken formula would have changed nothing (confirmed: both the stale production table and a freshly-regenerated local one topped out at the same ~1-20 magnitude).

**Fix**: switched the fold to a true cumulative sum (`n_observations = old + today`), re-documented `MAX_WINDOW_DAYS` as an independently-justified freshness policy rather than a decay-derived value (the number 20 is kept, just no longer tied to decay math), and updated the regression tests whose entire premise (fractional decayed values) no longer applied. Wiped and regenerated `reliability_buckets` from the real 90-day `arrival_events` history already on disk — **49,165 subway buckets now clear n≥200** (max 1621), real empirical citations can finally fire. Bus still tops out below 200 (max 80) — expected, not a bug: it only has ~3 weeks of real history since the 2026-09-22 restart (see that section above) and will cross 200 naturally as more days accumulate under the fixed formula. Pushed the corrected table to Railway's live `risk.sqlite3` via the same upsert-by-key the aggregator itself uses (`ON CONFLICT ... DO UPDATE`, keyed on the real unique index) — `monitored_trips` (real production trip data) was never touched by any of this, confirmed directly before and after.

**Rate limiting added to `/chat` and `/trip/plan`** (`app/rate_limit.py`, in-memory, no new dependency — this service runs as a single Railway instance): two tiers per the user's explicit ask ("stop a spike" vs. "block an abnormal source") — a 10-req/60s per-IP throttle (429, before any real Anthropic/OTP call happens), escalating to a full 10-minute block for an IP that trips the throttle 3 times within 10 minutes. Client IP read from `X-Forwarded-For` (Railway's edge forwards the real client IP there; `request.client.host` alone would just be Railway's internal proxy).

**OTP on-demand wake/sleep** (`app/otp_lifecycle.py`) — per the user's explicit ask ("only up and run if a routing request is made, including testing"). Deliberately **not** Railway's native `sleepApplication` feature: OTP is reachable only over private networking (`otp.railway.internal`, no public domain), and that feature wakes on traffic through a service's *public* edge domain — using it here risked a silent, permanent routing outage with no way to confirm it would ever wake. Built instead as an explicit control loop: `ensure_otp_awake()` before any OTP call (triggers a `serviceInstanceDeploy` restart and polls up to a 40s budget if not already reachable), `mark_otp_used()` after, and a periodic idle check (every 60s, cheap no-op when not applicable) that calls `deploymentStop` after 10 minutes of no routing requests. Both call sites (the `plan_route` tool dispatch, `/trip/plan`) degrade honestly when still starting — an error for the model to narrate, or an HTTP 503 — never a hang or a fabricated itinerary. **Real cold-start timing, measured twice**: an isolated test (stop+restart+poll, no LLM overhead) showed ~21-31s; a live end-to-end test through the actual `/chat` endpoint (genuine cold start, zero manual intervention) took 30s from wake-trigger to OTP responding, succeeding against the first-cut 25s poll budget only because the timing happened to land favorably — widened to 40s afterward, since the same live test proved the platform tolerates a 33s+ total request with no gateway timeout, so there was real headroom unused. **User's explicit choice**: reuses the existing personal-account `RAILWAY_API_TOKEN` (now also set on the `backend` service) rather than minting a narrower project-scoped token, accepting the wider blast-radius tradeoff for simplicity — if `backend` is ever compromised, this credential's reach extends to controlling Railway deployments in this project, not just this app's own data.

Only **Q90** (80%, ~23K records short) is still actively collecting; `CORRIDORS` in `bus_collector.py` is now just `["Q90"]`. The weekend-only gating (`_is_weekend()` in `main.py`) continues to self-resume/pause automatically with zero manual intervention — confirmed live: the hourly sync log shows a fresh file appearing within an hour of the UTC weekend boundary each time, unprompted.

## Transfer-risk model redesign + bus collection-target retirement (2026-10-12)

**Risk model, two user-directed changes, both now shipped in `app/risk_engine.py`:**

1. **`p_miss` and `typical_wait_seconds` are independently gated**, each off its own single bucket, instead of one compound Monte-Carlo-sampled number. `p_miss` = share of the INCOMING leg's delay/prediction-error histogram weight past the planned transfer buffer (exact closed-form sum over bin midpoints, no sampling). `typical_wait_seconds` = weighted-mean midpoint of the OUTGOING leg's headway histogram. Either can be citable while the other is "insufficient" — a real UX improvement, since a high-frequency outgoing route can tell a rider "~4 min either way" even when the incoming leg's own data is too thin to cite a percentage.
2. **No wait-time threshold/gate at all** (user, 2026-10-12: "I was being too overcomplicating... avoid the gate at all"). An intermediate design (shipped briefly, same day) made `should_offer_reroute` a rush-vs-non-rush minute threshold, then a user-urgency (`is_rush`/`user_in_a_rush`) flag instead of wall-clock rush hour — both now fully removed. Current behavior: `should_offer_reroute` is simply `typical_wait_seconds is not None`. The agent always pairs the miss percentage with the wait time and always asks if the rider wants a faster route calculated, regardless of how short or long the wait is — the rider decides, not a hardcoded cutoff. `get_risk()` takes no rush/urgency parameter of any kind.

`MIN_N_OBSERVATIONS` lowered from 200 to 50 (user, 2026-10-12) — statistically still catches a 5%+ true miss rate with ~92% probability (`1-0.95^50`), and real transfer-miss buckets are inherently scarcer than raw collected records (see next item), so 200 was an unnecessarily high bar for this specific use.

**Bus bucket granularity now follows real scheduled headways, not literal hour-of-day** (`app/bus_schedule_periods.py`, new file) — derives real per-route headway-by-hour from the static bus GTFS (trips/stop_times/calendar; MTA's bus GTFS has no `frequencies.txt`), then clusters adjacent hours into one period when consecutive hourly headways are within 30% of each other (anchored at hour 5). Subway buckets are unaffected (still literal hour_bucket). This directly fixes the earlier flat-24-buckets-per-day problem that was fragmenting already-scarce bus observations even further.

**Bus collection-target approach retired, replaced with direct measurement.** The per-route `BUS_COLLECTION_TARGETS` (raw 30s-poll record counts, assumed ~1:1 with derived `reliability_buckets` observations) was measured live and found wrong by **~17.4x** — Q90's busiest bucket: 365 raw records → only 21 real observations, because most raw records are repeated predictions for the same vehicle, not new events. Every "cleared target" stop decision made under that assumption (Q70+/M60+ on 10-01, B15/Q3/Q10 on 10-04, Q102/Q72/Q80 on 10-10) was therefore unreliable. Fix: `scripts/hourly_bus_sync.py` now has `real_bucket_coverage()`, which measures directly against `reliability_buckets` (what fraction of a route's real buckets clear `MIN_N_OBSERVATIONS`, split by weekday/weekend) instead of predicting from raw counts; `BUS_COLLECTION_TARGETS` is kept only as a stale historical comment, no longer consulted for stop decisions. **All 9 ever-collected corridors restored to active collection** (user, 2026-10-12: "keep collecting for all bus routes that is/was being collected") — `CORRIDORS` in `bus_collector.py` is now `["Q70+", "M60+", "Q102", "Q3", "B15", "Q10", "Q72", "Q80", "Q90"]`. Future per-route stopping should go through `real_bucket_coverage()`/`coverage_complete()`, not a raw-record proxy.

**Weekday-only collection pause (added 2026-10-05) also reverted, same day.** It paused `app/main.py`'s bus collector loop on weekdays (`_is_weekend()` gate) on the same now-retired "weekday targets already cleared" premise. Real measurement (`real_bucket_coverage()` run locally 2026-10-12, against the full local historical raw data) confirms every single corridor is far below `COVERAGE_COMPLETION_FRACTION` (0.90) on BOTH day types — e.g. Q70+ weekday 12/36 (33%) weekend 10/23 (43%); Q3 weekday 190/1102 (17%) weekend 156/786 (20%); Q90 weekday 29/60 (48%) weekend 28/107 (26%). `_is_weekend`/`BUS_COLLECTOR_WEEKDAY_CHECK_INTERVAL_S` removed from `main.py`; `_run_bus_collector_loop` now calls `run_forever()` unconditionally on every restart cycle, no day-of-week gate. Confirmed live via `railway ssh` before this fix was deployed: `/app/data/raw/bus/` was empty and un-written-to for 35+ seconds of observation (Monday, a weekday) — the pause was real and currently in effect on production, not just a latent risk. No stop marker (`/app/data/.bus_collection_complete`) was present, so the collector resumes collecting all 9 corridors immediately once this fix deploys.

**Weekend folded into weekday for schedule-equivalent hours (user, 2026-10-12): "if the bus data collection is schedule interval-based, why discriminate between weekday and weekend?"** `app/bus_schedule_periods.py` gained `effective_day_type_and_hour(route_id, day_type, hour)`: for any hour where a route's real weekday and weekend scheduled headway are within `PERIOD_MERGE_TOLERANCE` of each other, weekend observations fold into the SAME bucket as weekday (canonicalized to "weekday"), pooling observations from all 7 days of the week instead of splitting them 5/7 vs 2/7. Verified against real GTFS before implementing: B15 has equivalent weekday/weekend headway on **23 of its 24 scheduled hours** (effectively one schedule, not two) — Q3 on 11/24, Q80 on 6/24, others less. `aggregate_reliability_buckets.py`'s `_effective_day_type_and_hour` and `risk_engine.py`'s `_compute_transfer_risk` both route through this per-route (not assumed route-wide), since each route's equivalence pattern differs. Local `reliability_buckets` was wiped and regenerated for bus only (subway untouched, confirmed by row count before/after) to apply this to all existing history, then pushed to Railway's live `risk.sqlite3` the same DELETE-by-agency+INSERT way the earlier hour-to-period migration was pushed (confirmed before/after: bus 7933→6774 rows, subway 148163 unchanged both sides).

**A genuinely mixed result, reported honestly rather than oversold:** the regen also surfaced that this session's earlier collection-timeline estimate (the "336 days for the slowest corridor" figure) was partly built on a `reliability_buckets` table that had accumulated inconsistent state from this session's OWN repeated code changes (the hour-to-period migration, the zip-skip-continue fix, etc. all ran `categorize_bus_data()` against the same incrementally-evolving table) — the clean single-pass regen is a more trustworthy baseline than that estimate was. Separately, the day-type merge's effect on the **90%-of-distinct-buckets** completion metric was NOT a clean win on its own: it disproportionately removed the easy, well-populated buckets from each day type's uncleared pool (e.g. B15 weekend dropped from 1082 to 259 total distinct buckets), concentrating what was left in the genuinely schedule-divergent (usually rush-hour, or — see next item — late-night) slots that were always going to be the slow stragglers. The late-night exclusion below resolves most of this directly.

**Late-night bus citations disabled for a narrow 2:00am-3:59am window (user, 2026-10-12): "almost nobody rides a bus at 2am thus almost nobody is using our service" for it.** First cut suppressed everything before `bus_schedule_periods.ANCHOR_HOUR` (5am) — **corrected same day**, user: "people start riding buses/subways at 4am to catch early flights and go to work," so 4am is a real, separate rider population this product must keep serving. `risk_engine.LATE_NIGHT_SUPPRESSED_HOURS = frozenset({2, 3})` is now its own constant, decoupled from `ANCHOR_HOUR` (a different concept — where that module's hour-*clustering* walk starts, not a citation policy). `_is_late_night_bus(agency, hour)` suppresses fetching/citing (both `p_miss` and `typical_wait_seconds`) only for a bus leg whose real literal hour is 2 or 3. Collection itself is untouched (the collector has no time-of-day filter, data is free to keep) — only citing is skipped, degrading the same way any other no-data case does (`quality="insufficient"`, `typical_wait_seconds=None`), never a fabricated number. Subway is unaffected (it runs a real, if reduced, overnight service with real riders). `hourly_bus_sync.py`'s `real_bucket_coverage()` imports the same `LATE_NIGHT_SUPPRESSED_HOURS` constant (no drift between the two) and excludes those hours from its denominator — approximate for bus, since a stored `hour_bucket` is period-mapped rather than literal, so this excludes whichever PERIOD a suppressed literal hour lands on; coarse but consistent with every other policy choice in this file, not worth a more precise literal-hour reconstruction for a 2-hour window. Deliberately **not** weighted by real observed traffic volume beyond this (user, 2026-10-12: "don't make this too hard... collect until the data can produce a sensible probability") — the existing per-bucket `n_observations >= MIN_N_OBSERVATIONS` gate already is "collect until the data can produce a sensible probability." **Real status as of this fix** (`real_bucket_coverage()`, local data): no corridor has reached `COVERAGE_COMPLETION_FRACTION` (0.90) on the bucket-count metric yet — weekend is the universal bottleneck, with per-route estimated calendar-days-to-90% ranging from ~77 (Q70+) to ~420 (Q72), dominated by long-tail low-traffic slots. A more rider-relevant view (real observation volume already landing in a citable bucket, not distinct-bucket count) is much healthier: M60+ 93%, B15 94%, Q90 96%, Q102 92%, Q3 88%, Q10 87%, Q80 82%, with Q70+ (75%) and Q72 (75%) lagging — most of what riders will actually query is already citable even though the distinct-bucket-count metric says otherwise.

**Clarifying day_type after all these changes: it's still a real schema column, but no longer a blanket always-split dimension.** Every bucket is still tagged `weekday` or `weekend` in the database, but which hours actually end up SEPARATE is now driven entirely by each route's real scheduled-interval evidence (`bus_schedule_periods.py`), the same way hour-of-day granularity already was: hours where weekday and weekend headway are equivalent collapse onto one shared row; hours where they genuinely differ (and aren't excluded as late-night) stay split. "Scheduled interval buckets" describes the whole system now — day_type is just one more axis that collapses or stays split based on the same real-interval-equivalence test as everything else, not a separate always-on split.

**`find_stop` fuzzy-matching gap fixed (2026-10-12).** `StopIndex.find_by_name` was a literal case-insensitive substring check, so "Lexington Av 63" didn't match the real GTFS name "Lexington Av/63 St" purely because `/` breaks character-for-character contiguity. Fixed with `_normalize_for_search` in `app/routing/nearest_stop.py`: collapses every run of non-alphanumeric characters (punctuation, slashes, extra spaces) to a single space on both sides of the comparison before the substring check — still a deterministic substring match, no edit-distance/probabilistic fuzzy matching.
